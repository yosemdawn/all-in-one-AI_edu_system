# 项目需求文档：智能批分助手

## 1. 项目概述

### 1.1 项目背景
本项目旨在为教育工作者提供一个高效、自动化的答题卡批量批阅工具。传统的人工批阅方式耗时耗力且容易出错。通过利用先进的大语言模型（LLM）的多模态能力，本工具能够直接从答题卡图片中识别学生信息和作答内容，并根据预设的标准答案自动评分，最终生成结构化的成绩报告。

### 1.2 项目目标
- **核心变更**：完全移除对传统OCR服务的依赖（如百度OCR），将答题卡的文字识别、关键信息提取（姓名、题号、答案）等任务全部交由豆包LLM处理。
- **自动化与效率**：实现从上传答题卡图片到生成详细成绩报告的全流程自动化，显著提升批阅效率。
- **准确性与灵活性**：在保证高识别准确率的同时，保留严格的评分规则（如选择题、填空题的精确匹配）。
- **易用性**：提供简洁直观的Web用户界面，方便用户录入标准答案、上传文件、查看和导出成绩。
- **本地化运行**：支持在本地环境中轻松部署和运行，确保数据隐私和安全。

## 2. 功能需求

### 2.1 系统配置
- **FR1.1 - 密钥管理**：用户应能够在系统配置中（如 `.env` 文件或前端设置界面）输入并保存豆包LLM的API Key和Secret Key，用于后续的API调用。

### 2.2 标准答案管理
- **FR2.1 - 答案录入**：用户应能通过界面为不同题号录入标准答案。
- **FR2.2 - 题型支持**：支持至少两种题型：
    - **单项选择题**：答案为单个大写字母（如 A-F）。
    - **填空题**：答案为具体的文本字符串。
- **FR2.3 - 答案持久化**：用户录入的标准答案应能保存在浏览器本地存储（localStorage）中，方便下次使用。

### 2.3 答题卡处理与评分
- **FR3.1 - 文件上传**：用户应能一次性上传多张图片格式（JPG, PNG）的答题卡文件。
- **FR3.2 - 多模态识别与解析**：
    - 系统接收到图片后，应直接调用豆包LLM的多模态接口。
    - LLM负责识别图片中的所有文字，并根据预设的提示（Prompt）智能提取结构化信息。
    - LLM必须返回每张图片对应的JSON对象，包含以下关键字段：
        - `name`: 学生姓名。
        - `answers`: 一个对象，键为题号（字符串），值为该题对应的学生答案（字符串）。
    - 如果LLM无法识别或解析某张图片，应返回明确的错误信息。
- **FR3.3 - 自动评分**：
    - 系统使用LLM返回的结构化作答结果，与用户录入的标准答案进行比对。
    - **评分规则**：
        - **选择题**：学生答案必须与标准答案完全一致（严格区分大小写）。
        - **填空题**：学生答案在去除首尾空白后，必须与标准答案完全一致（严格区分大小写、全半角）。
        - **分值体系**：遵循预设的题目分值区间（例如：1-15题每题3分，16-30题每题1分等）。
        - **缺答/空白**：计0分。

### 2.4 成绩展示与导出
- **FR4.1 - 结果展示**：评分完成后，界面应清晰地展示每位学生的总分以及每道题的得分详情。
    - 详情应包括：题号、题目类型、标准答案、学生答案、是否正确、得分。
- **FR4.2 - 数据导出**：用户应能将所有学生的成绩报告一键导出为CSV文件。
    - CSV文件应包含表头，并能被Microsoft Excel等软件正常打开且不出现乱码（UTF-8 with BOM 格式）。

## 3. 非功能性需求

- **NF1 - 性能**：系统应能流畅处理中等规模的批量上传（例如一次处理50张图片），并在合理的时间内返回评分结果。
- **NF2 - 易用性**：用户界面应简洁明了，操作流程符合直觉，无需复杂的学习过程。
- **NF3 - 兼容性**：前端界面应兼容主流的现代浏览器（如 Chrome, Firefox, Edge）。
- **NF4 - 部署**：项目应能通过简单的命令（如 `npm install` 和 `npm run dev`）在标准的Node.js环境中启动。

## 4. 系统架构与接口

### 4.1 系统架构
系统采用前后端分离架构：
- **前端**：原生HTML, CSS, JavaScript，负责用户交互、答案录入、文件上传和结果展示。
- **后端**：Node.js + Express + TypeScript，负责处理业务逻辑，包括接收文件、调用LLM接口、执行评分和生成导出文件。

### 4.2 API接口变更
- **原 `/api/ocr` 接口将被重构或替换**。新的接口（例如 `POST /api/process`）将承担核心处理任务。
- **`POST /api/process`**
    - **请求 (Request)**：
        - `form-data`:
            - `files`: 多个图片文件。
            - `doubaoApiKey` / `doubaoSecretKey` (可选): 用于在未配置环境变量时临时传入密钥。
    - **响应 (Response)**：
        - 返回一个包含结构化解析结果的数组，每个元素代表一个文件，格式如下：
        ```json
        {
          "items": [
            {
              "filename": "张三_答题卡.jpg",
              "parsed": {
                "name": "张三",
                "answers": { "1": "A", "2": "B" }
              }
            },
            {
              "filename": "李四_答题卡.jpg",
              "error": "未能识别此答题卡中的有效信息。"
            }
          ]
        }
        ```
- **`/api/grade` 和 `/api/export` 接口保持不变**，但其输入数据将直接来源于 `/api/process` 接口的成功输出。
